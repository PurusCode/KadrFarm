# Двухпроходная визуальная режиссура KadrFarm

Статус: проект Stage I; независимая спецификация, не подключённая к production.
Версия промптов: `global-v2` и `scene-v2`.

## 1. Задача архитектуры

KadrFarm должен создавать цельный авторский видеорассказ. Визуальные решения обязаны развиваться вместе с содержанием дикторской дорожки. Нельзя производить набор независимых картинок, равномерно разложенных по времени.

Дикторский рассказ остаётся самостоятельным каналом объяснения: все важные факты, числа, причинные связи и выводы должны быть понятны без изображения. Кадр усиливает и иллюстрирует речь, но не заменяет её.

Stage I разделён на два прохода:

1. `VisualStoryPlan` — один глобальный ответ модели на всю раскадровку.
2. `SceneCompositionPlan` — отдельный ответ на каждую сцену, последовательно, с глобальным планом и уже проверенной историей предыдущих сцен.

Промпты и request builders находятся в `src/kadr_farm/visual_story_prompts.py`. Они не вызывают модель, не создают журнал и не импортируют production-директор. Их можно проверить независимо.

## 2. Источники истины

Вход первого прохода строится из `storyboard.py` и его фактического результата:

- `title`;
- `source_script_sha256`;
- упорядоченный `scenes[]`;
- в каждой сцене: `id`, `block_id`, `meaning`, `purpose`, `voice_text`.

`scene_id` и `voice_text` неизменяемы. Модель не может добавлять, пропускать, переставлять или переписывать сцены.

Доверенные числовые факты не извлекаются из режиссёрского ответа. `ApprovedFact` и `DataProvenance` должны быть сформированы внешним проверяющим этапом/редактором. Scene Director получает только разрешённый каталог вычисленных значений и может ссылаться на `value_id`. Он не может создавать `fact_id`, URL или повышать статус проверки.

## 3. Проход 1 — Global Director

### Вызов

- schema: `VisualStoryPlan` v1.1;
- task_id: `visual_story:global:global-v2`;
- stage: `visual_story_global`;
- один запрос для всего ролика — не разбивать сцены на независимые batch-вызовы;
- стартовый лимит ответа `max_tokens=8500`, параметр можно явно переопределить после
  проверки лимитов выбранной модели;
- системный промпт: `GLOBAL_SYSTEM_PROMPT`;
- пользовательский prompt создаёт `build_global_director_request()`.

Промпт получает все сцены в исходном порядке с полным текстом диктора. JSON Schema передаётся `StructuredLLMRouter` из самой Pydantic-модели `VisualStoryPlan`; schema не дублируется вручную в строке промпта. После Pydantic-ответа orchestrator обязан сразу вызвать `validate_global_plan_coverage(storyboard, plan)`: эта проверка сверяет точные scene IDs/порядок, минимальную долю развивающих сцен (по умолчанию 0.5) и фактический повтор хотя бы одного мотива для историй от трёх сцен. Только после её успеха разрешается начинать Pass 2. При семантическом отказе task надо пометить `journal.reject_task(GLOBAL_TASK_ID, reason)`, чтобы Pydantic-валидный, но редакторски отклонённый ответ не использовался из кэша.

### Выход

`VisualStoryPlan` определяет:

- единый стиль;
- упорядоченную сюжетную дугу `arc`;
- реестр смысловых мотивов;
- `visual_thesis` — единый визуальный принцип всего ролика;
- `arc_summary` — описание изменения этого принципа от начала до финала;
- для каждой сцены: `narrative_role`, `purpose`, `visual_intent`, отношение к предыдущей сцене, развиваемую сцену и мотивы.

Пример сокращённого, но валидного двухсценного плана:

```json
{
  "schema_version": "1.1",
  "visual_thesis": "Одна финансовая цель постепенно превращается из вопроса в проверяемый расчёт.",
  "arc_summary": "История начинается с неопределённой цели, показывает исходные расходы и раскрывает способ расчёта необходимого капитала.",
  "style": {
    "palette": ["#fdf3dc", "#e8862e"],
    "font_family": "Segoe UI",
    "tone": "warm",
    "grain": true,
    "caption_style": "card"
  },
  "arc": ["s_001", "s_002"],
  "motifs": [
    {
      "motif_id": "motif_capital",
      "kind": "counter",
      "description": "Счётчик финансовой цели, который постепенно наполняется",
      "first_scene": "s_001",
      "returns_in": ["s_002"]
    }
  ],
  "scenes": [
    {
      "scene_id": "s_001",
      "narrative_role": "hook",
      "purpose": "Поставить главный вопрос ролика",
      "visual_intent": "Ввести счётчик как наглядный образ финансовой цели",
      "relation_to_previous": "introduces",
      "develops_scene_id": null,
      "motif_ids": ["motif_capital"],
      "link_prev": null,
      "link_next": "s_002"
    },
    {

```

Для реальных роликов с тремя и более сценами валидатор по умолчанию требует как минимум один фактически возвращающийся мотив. Возвращение должно быть содержательным; нельзя объявлять мотив повторяющимся только потому, что сцена находится в `arc`.

## 4. Проход 2 — Scene Director

Проход выполняется последовательно по сценам. Одна сцена — одна задача, чтобы сбой или исправление затрагивали только одну композицию. При этом каждый запрос получает компактное представление всей глобальной режиссуры, соседние сюжетные роли и реестр ранее созданных композиций.

### Вызов

- schema: `SceneCompositionPlan`;
- task_id: `visual_story:scene:<scene_id>:scene-v2`;
- stage: `visual_story_scene`;
- стартовый лимит ответа `max_tokens=7000`, его можно явно увеличить для сложной сцены
  после проверки ограничений модели;
- системный промпт: `SCENE_SYSTEM_PROMPT`;
- пользовательский prompt создаёт `build_scene_composition_request()`.

Перед генерацией builder требует, чтобы `previous_scene_plans` были уже проверенным непрерывным префиксом исходной раскадровки. Для сцены `s_004` необходимо передать планы `s_001`, `s_002`, `s_003` именно в этом порядке. Builder повторно запускает семантическую проверку этого префикса через `validate_scene_composition_prefix()`: точные мотивы, состояние продолжаемых объектов, ссылки `develops`, числовые данные и речевые якоря. Этот helper также следует вызывать сразу после каждого ответа Scene Director; при отказе вызвать `journal.reject_task()` для task ID текущей сцены. Если предыдущий план структурно валиден, но семантически противоречит Global Plan, следующий запрос не создаётся. Порог доли развивающих композиций и требование повторяющегося мотива откладываются до полной истории, чтобы ранний короткий префикс не отклонялся преждевременно.

### Контекст запроса

Каждая сцена получает:

- весь Global Plan в компактном виде, включая `visual_thesis` и `arc_summary`;
- точную исходную сцену и её `SceneDirection`;
- направления предыдущей и следующей сцен;
- ID и состояние всех прежних композиций в компактном индексе;
- более подробный контекст последних трёх уже проверенных сцен;
- список разрешённых значений с единицами измерения, статусом, `fact_id` и URL источника;
- стабильный beat ID и точные текстовые границы candidate speech units.

### Пример результата второго прохода

Для этого примера `voice_text` сцены `s_002` — `Вернёмся к счётчику. Умножь расходы на двадцать пять.`. Детерминированный разделитель формирует candidate units с границами `(0, 21)` и `(21, 53)`. ## 5. Речь и временная шкала

`build_speech_registry()` создаёт детерминированный beat ID на сцену (`<scene_id>_voice`) и candidate units из исходного `voice_text`. Их границы нужны, чтобы модель могла выбирать полные смысловые фрагменты и не обрезала слово посередине.

Эти candidate units **не являются измеренными временными интервалами**. Builder не выдумывает длительности и не присваивает WAV hash. `resolve_action_schedule()` позднее требует у каждой единицы фактические `duration_sec` и SHA-256 отдельного WAV. Глобальная шкала строится суммированием длительностей всех предыдущих единиц в `beat_order`.

Следовательно, пока действующий TTS-конвейер не синтезирует и не сохраняет отдельные WAV для этих единиц (либо не использует проверенное forced alignment), нельзя запускать реальное исполнение их посегментного расписания. Наличие пунктуации само по себе не доказывает временную границу.

## 6. Повторяемость и восстановление

`StructuredLLMRouter.complete()` уже вычисляет fingerprint из JSON Schema, системного и пользовательского промптов, температуры, лимита токенов и выбранных provider/model/endpoint. При наличии `ProductionJournal` успешный ответ повторно используется только при совпадении fingerprint.

Назначенные task IDs:

- `visual_story:global:global-v2` — один глобальный запрос;
- `visual_story:scene:s_001:scene-v2` — композиция s_001;
- `visual_story:scene:s_002:scene-v2` — композиция s_002;
- и далее для каждой сцены.

Изменение глобального плана меняет текст контекста в каждом новом запросе Scene Director и, следовательно, fingerprint. Старые scene results не должны переиспользоваться при другом глобальном плане. Изменение prompt version или схемы также создаёт другой fingerprint.

Builder не выбирает провайдера и не создаёт `ProductionJournal`. В будущем orchestration layer должен:

1. закрепить provider/model/endpoint на весь run через существующую production policy;
2. создать один `ProductionJournal` на тот же `--out`;
3. отправить один global task;
4. валидировать Global Plan против точного списка входных scene IDs;
5. последовательно отправить scene tasks с уже проверенным префиксом;
6. после второго прохода выполнить полный `validate_plan()` против beat registry, approved facts и обоих наборов планов;
7. повторно проверить всю историю через `validate_plan()` с полным beat registry и approved facts; при ошибках отклонить затронутые задачи через `journal.reject_task()` и не создавать финальный Stage I manifest;
8. только при нулевых validation errors сохранить финальный Stage I manifest.

Никакого автоматического переключения primary/secondary не добавлять.

## 7. Ограничения текущего этапа

- Промпты пока не подключены к `production_director.py`.
- Этот этап не синтезирует WAV и не выполняет композицию/рендер.
- Реальные факты и их verified-статусы не могут рождаться внутри режиссёрского промпта.
- Глобальный запрос один; если провайдер не может вместить весь исходный ролик или JSON-ответ, это должно диагностироваться как ограничение модели/контекста, а не скрытно заменяться независимыми batch-планами.
- Pass 2 выполняет одну сцену за запрос, но получает глобальный план и историю предыдущих композиций.
- Редакторские пороги `validate_plan()` остаются явными параметрами. Их нельзя ослаблять автоматически, чтобы заставить неудачный ответ пройти.
