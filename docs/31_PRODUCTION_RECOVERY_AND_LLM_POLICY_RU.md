# Сохранение прогресса и восстановление производства KadrFarm

Дата решения: 19.11.2026
Статус: принято; первый технический слой внедряется в основной production director.

## 1. Архитектурное решение

Качество результата приоритетнее скорости и формального завершения задания. Производство не должно незаметно заменять основную модель локальной или другой моделью с непроверенным качеством.

В production director по умолчанию используется только провайдер `primary` (MWS в текущей конфигурации). Выбор `secondary` разрешается только явной настройкой `KADR_PRODUCTION_LLM_PROVIDER=secondary`. Автоматический fallback между моделями в этом конвейере отключён. Это не запрещает использовать вторую модель после осознанного решения оператора; это исключает скрытую смену модели после тайм-аута.

Ошибка внешнего API, тайм-аут, невалидный ответ, локальная ошибка валидации и ошибка загрузки/рендеринга должны оставлять диагностируемое состояние. Производство возобновляется с первой незавершённой или невалидной контрольной точки, а не пересоздаётся целиком.

## 2. Где хранятся результаты

Для каждого запуска `--out <каталог>` создаётся:

```text
<out>/recovery/
├── production_state.json       # состояние запуска, этапов и задач
├── model_calls/                # полный запрос, исходный ответ и метаданные каждого вызова
└── llm_results/                # только успешно проверенные структурированные ответы
```

`production_state.json` хранит текущий/последний этап, его статус, счётчики попыток, ошибку и ссылки на артефакты. Каждый вызов модели сохраняется отдельным JSON до разбора и Pydantic-валидации. Поэтому сохраняется даже синтаксически неправильный, обрезанный или пустой ответ, а также причина ошибки API.

В артефакте вызова сохраняются системный и пользовательский промпты, схема, температура, лимит токенов, провайдер, модель, raw response, finish reason, usage и доступные поля refusal/thinking. Ключи API и заголовки авторизации не сохраняются.

Успешный ответ можно повторно использовать только при совпадении fingerprint полной задачи: схемы, обоих промптов, параметров генерации и выбранного провайдера/модели/endpoint. Изменение входа, редакторских правил или выбранной модели инвалидирует соответствующую контрольную точку. Ответ, прошедший Pydantic, но отклонённый последующей проверкой (например, по набору scene_id или точному покрытию дикторского текста), получает статус `rejected` и не используется повторно как готовый результат.

## 3. Возобновление

Оператор повторно запускает ту же команду с тем же `--out`. Система:

1. отмечает предыдущий незавершённый этап как `interrupted`;
2. использует только завершённые результаты с совпадающими fingerprint;
3. пропускает уже готовые LLM-задания;
4. повторяет неуспешное задание, сохраняя новые попытки отдельными артефактами;
5. повторно проверяет локальные кэши файлов по пути и SHA-256.

Успешные ответы не перезаписываются неудачной повторной попыткой. Предыдущие сырые ответы остаются в `model_calls/`.

## 4. Разделение ошибок

- Тайм-аут/сеть: сохранить состояние и повторить это же задание после восстановления связи либо осознанно выбрать проверенный `secondary`.
- Пустой/обрезанный/некорректный JSON: сохранить raw response и метаданные; выполнить ограниченную попытку исправления, также сохранив её отдельно. Если исправление не прошло, остановиться на этой задаче.
- Ошибка схемы или редакторской проверки: повторять только соответствующее задание/план, не весь выпуск.
- Ошибка Pixabay: повторить загрузку конкретного визуального beat; готовые WAV и визуалы не создавать заново.
- Ошибка рендеринга/сборки: повторить соответствующий этап, используя уже сохранённые планы, озвучку и исходные визуалы.

Автоматический fallback на локальную модель не является обработчиком ошибки. Он может изменить художественное качество и потому требует явного решения человека.

## 5. Контрольные точки

Существующие resumable-планы режиссёра и shot planner сохраняются. К ним добавляются:

- журнал и fingerprint-кэш структурированных LLM-вызовов для storyboard, director, critic, repair, shot planner и source audit;
- кэш WAV Kokoro по ID фрагмента, хэшу исходной и нормализованной речи, скорости, голосу и revision модели;
- кэш визуального результата каждого beat с fingerprint входа, проверкой наличия файла и SHA-256;
- состояние этапов pipeline и диагностика последнего незавершённого этапа.

После изменения входного текста, скорости TTS или режиссёрского плана соответствующие зависимые артефакты автоматически признаются устаревшими по fingerprint. Неизменившиеся независимые задания повторно использовать можно.

## 6. Выбор модели

По умолчанию:

```dotenv
KADR_PRODUCTION_LLM_PROVIDER=primary
```

Чтобы намеренно выполнить запуск через настроенный вторичный провайдер:

```dotenv
KADR_PRODUCTION_LLM_PROVIDER=secondary
```

Это выбор провайдера для всего production-run, а не автоматическое переключение при сбое. Сначала необходимо отдельно оценить качество `secondary` на едином редакторском тесте. Значение по умолчанию `primary` не означает, что тайм-аут нужно устранить снижением качества или бесконечным ожиданием: нужно использовать конечный, осознанно настроенный timeout и возобновление.

## 7. Эксплуатационные ограничения и безопасность

- Для возобновления указывайте тот же каталог `--out`. Новый каталог начинает независимое производство.
- Каталог `output/` исключён из Git. Сырые запросы и ответы могут содержать сценарий и пользовательские материалы; не публикуйте их вместе с исходным кодом.
- Модельные raw-ответы являются диагностическими данными, а не утверждённым содержанием. В production используются только ответы, прошедшие локальную схему и предметные проверки.
- Фактчекинг по-прежнему требует проверки человеком; этот механизм не повышает автоматически статус фактов.
- Контрольные точки не делают сеть, Pixabay или FFmpeg безошибочными. Они ограничивают повторную работу и сохраняют точное место сбоя.

## 8. Критерий приёмки первого слоя

1. Каждый ответ LLM сохраняется отдельно до JSON/Pydantic validation.
2. Повторный запуск повторно использует завершённое задание только при совпадающем fingerprint.
3. Тайм-аут основной модели не переключает production-run на локальную модель.
4. Прерывание оставляет `production_state.json` с последним незавершённым этапом.
5. Kokoro не пересинтезирует валидные WAV, а визуальный production не пересоздаёт валидные beat assets.
6. Смена сценария/голоса/скорости/плана инвалидирует связанные кэши.
